# فوس — إعداد اشتراكات Tap المتجددة

هذه الحزمة تجعل الباقتين اشتراكًا متجددًا تلقائيًا:

- 19 ر.س كل 30 يومًا (`access_30_days`).
- 39 ر.س كل 90 يومًا (`access_90_days`).

الدفع الأول يتم في صفحة Tap المستضافة مع 3D Secure وحفظ البطاقة لدى Tap. فوس لا يرى رقم البطاقة ولا يخزّنه. عند موعد التجديد ينشئ الخادم رمزًا مؤقتًا للبطاقة المحفوظة، ثم ينفذ Merchant-Initiated Transaction بالمبلغ الثابت للباقة.

عندما يختار العميل «إيقاف التجديد» قبل موعد التجديد، لا يحدث الخصم التالي وتبقى المزايا متاحة حتى نهاية المدة المدفوعة. إذا وصل الإلغاء بعد حلول الموعد وكانت معالجة الدورة المستحقة قد بدأت، فقد تكتمل تلك الدورة ويتوقف ما بعدها. الإلغاء ليس استرجاعًا للمبلغ.

## تنبيه مهم قبل الدفع الحقيقي

الحزمة جاهزة للاختبار في Tap Sandbox، وليست جاهزة لاستقبال أموال حقيقية بمجرد رفعها. قبل التحويل إلى Live يجب أن يؤكد مدير حساب Tap تفعيل الميزتين التاليتين على حساب التاجر:

1. **Save Card** وإرجاع `Customer ID` و`Card ID` و`Payment Agreement ID` بعد الدفعة الأولى.
2. **Merchant-Initiated / non-3DS recurring charges** في البيئة الحقيقية.
3. صلاحية **Saved Card Token API** للحساب، وما إذا كان Tap يتطلب شهادة PCI أو تفعيلًا خاصًا للوصول إليه؛ أكّد ذلك كتابيًا مع مدير الحساب قبل Live.

وثائق Tap العامة تشرح أن `save_card: true` في أول عملية يولّد بيانات البطاقة المحفوظة واتفاقية الدفع، لكنها لا تعرض في الصفحة العامة مخطط طلب موثّقًا لإنشاء نوع عقد Subscription مخصص. لذلك لا تفترض الحزمة شكلاً غير موثّق: تشترط رجوع المعرّفات الثلاثة، وترسل `Payment Agreement ID` في كل تجديد. اختبر الرد الفعلي مع Tap واطلب منهم اعتماد التكامل قبل Live.

لا تضع مفتاح Tap أو Supabase السري أو `CRON_SECRET` في المحادثة أو داخل ملفات الواجهة.

## 1. قاعدة بيانات Supabase

1. افتح **SQL Editor** في مشروع Supabase.
2. شغّل ملف `supabase/schema.sql` كاملًا.
3. من **Authentication → URL Configuration** اضبط:
   - Site URL: `https://phoslearn.vercel.app`
   - Redirect URLs: رابط الموقع النهائي المسموح.
4. انسخ Project URL والمفتاح العام للواجهة والمفتاح السري للخادم.

المخطط يمنع المتصفح من قراءة معرّفات الدفع المحفوظة أو تعديل الطلبات والاشتراكات، ويجعل التفعيل والإلغاء وحجز التجديد عمليات خادمية فقط. لا تشغّل مخطط مزود الدفع القديم مع هذه الحزمة.

## 2. تهيئة Tap Sandbox

من لوحة Tap أو عبر مدير الحساب احصل على:

- Secret API key يبدأ بـ `sk_test_`.
- Merchant ID الخاص بالحساب نفسه.
- تفعيل Save Card وMerchant-Initiated Transactions للاختبار.

لا يحتاج المتصفح إلى مفتاح Tap عام لأن الدفع الأول يفتح صفحة Tap المستضافة. عنوان الـ webhook يُرسل داخل كل Charge وهو:

`https://phoslearn.vercel.app/api/tap-webhook`

الخادم يتحقق من `hashstring`، ثم يجلب العملية من Tap مرة أخرى؛ لا يمنح الوصول اعتمادًا على بيانات المتصفح أو جسم الـ webhook وحده.

## 3. متغيرات Vercel

أضف القيم التالية من **Project Settings → Environment Variables**:

| المتغير | الاستخدام |
|---|---|
| `VITE_SUPABASE_URL` | رابط مشروع Supabase |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | المفتاح العام للواجهة |
| `VITE_SUPPORT_EMAIL` | بريد خدمة العملاء الظاهر في السياسات؛ القيمة المعتمدة حاليًا `phoslearn@gmail.com` |
| `SUPABASE_URL` | رابط مشروع Supabase نفسه |
| `SUPABASE_SECRET_KEY` | المفتاح السري للخادم فقط |
| `TAP_SECRET_KEY` | `sk_test_...` للاختبار ثم `sk_live_...` بعد الاعتماد |
| `TAP_MERCHANT_ID` | Merchant ID المطابق للمفتاح |
| `TAP_LIVE_MODE` | `false` للاختبار، ثم `true` فقط عند Live |
| `APP_URL` | `https://phoslearn.vercel.app` بلا مسار إضافي |
| `CRON_SECRET` | سر عشوائي لا يقل عن 32 محرفًا؛ Vercel يرسله تلقائيًا للـ Cron |
| `TELEGRAM_COMMUNITY_URL` | رابط دعوة جديد للمجتمع الخاص |
| `PHOS_AI_ORIGIN` | رابط خدمة الذكاء الاصطناعي |
| `PHOS_AI_ALLOWED_HOSTS` | اسم المضيف المسموح فقط، دون `https://` |
| `PHOS_AI_PROXY_SECRET` | سر مختلف بين Vercel وخدمة الذكاء الاصطناعي |
| `PHOS_AI_MODEL` | اسم النموذج الذي تستخدمه الخدمة |

ولّد الأسرار محليًا مثلًا:

```bash
openssl rand -hex 32
```

ملف `.env.example` أمثلة فقط. لا ترفع ملف `.env` الحقيقي إلى المستودع.

## 4. النشر والجدولة

في Vercel اختر Vite، مع:

- Build command: `npm run build`
- Output directory: `dist`
- Node.js: 22.x
- خطة Vercel المناسبة لنشاطك. الإعداد الحالي يستخدم Cron يوميًا بما يتوافق تقنيًا مع حدود Hobby، لكن تحقّق من شروط Vercel التجارية واختر خطة مدفوعة إذا تطلبها استخدامك.

يحتوي `vercel.json` على Cron يعمل يوميًا عند الساعة 00:05 بتوقيت UTC للمسار `/api/renew-subscriptions`، ويعالج حتى 50 استحقاقًا في التشغيل بدُفعات متوازية محدودة. وظيفة التجديد مضبوطة على `maxDuration: 300` ثانية مع Fluid Compute. راقب سجل Cron؛ Vercel يصف تسليمه بأنه best-effort ولا يعيد التشغيل الفاشل تلقائيًا، لذلك عالج أي تشغيل فاشل فورًا وشغّله يدويًا عند الحاجة.

التجديد لا يُخصم مبكرًا: لا يُحجز إلا عند أو بعد `current_period_end`. توجد مهلة تقنية مقدارها 48 ساعة للمشترك الذي ما زال التجديد مفعّلًا؛ تظل المزايا متاحة مؤقتًا أثناء المحاولة، ولا ينشئ النظام خصمًا جديدًا بعد نهاية هذه النافذة. قد تصل لاحقًا نتيجة نهائية لمحاولة بدأت داخل النافذة؛ تُصالح العملية نفسها دون إنشاء خصم آخر. الفترة الجديدة تُحسب من نهاية الفترة السابقة، لا من وقت تشغيل Cron.

الإلغاء يستخدم قفل قاعدة البيانات نفسه الذي يستخدمه حجز التجديد. إذا أوقف العميل التجديد قبل نهاية المدة فلن تُنشأ دورة جديدة. إذا وصل الطلب بعد نهاية المدة، فالدورة التي أصبحت مستحقة تُعالج مرة واحدة حتى لو لم يصلها Cron بعد، ثم يتوقف ما بعدها. وأي طلب تجديد حُجز وبدأت معالجته لا يُلغى محليًا أثناء الطريق؛ تتم مصالحته مع Tap ثم يبقى التجديد اللاحق متوقفًا.

إذا انقطع اتصال الخادم أثناء إنشاء الدفعة الأولى ولم يرجع `Charge ID`، يحتفظ النظام بالطلب كحالة ملتبسة ولا يفتح محاولة ثانية قد تسبب خصمًا مزدوجًا. ابحث في لوحة Tap باستخدام `reference.transaction` أو `reference.order`، ثم أعد إرسال webhook للعملية الصحيحة أو عالجها مع دعم Tap؛ لا تغيّر الطلب إلى `expired` يدويًا قبل التأكد أنه لم يُنشأ لدى Tap.

## 5. حماية المزايا المدفوعة

- `/api/ai` و`/api/community` يتحققان من جلسة Supabase ومن العضوية على الخادم.
- مفتاح خدمة الذكاء الاصطناعي ورابط مجتمع تيليجرام لا يدخلان حزمة JavaScript العامة.
- يجب أن ترفض خدمة الذكاء الاصطناعي أي طلب لا يحمل `X-Phos-Proxy-Secret` الصحيح.

مثال الفحص داخل الـ Worker:

```js
const supplied = request.headers.get("X-Phos-Proxy-Secret");
if (!env.PHOS_PROXY_SECRET || supplied !== env.PHOS_PROXY_SECRET) {
  return new Response("Unauthorized", { status: 401 });
}
```

استخدم القيمة نفسها في `PHOS_PROXY_SECRET` لدى الـ Worker و`PHOS_AI_PROXY_SECRET` لدى Vercel.

رابط تيليجرام ثابت وقابل للمشاركة بعد كشفه لمشترك. ألغِ الرابط القديم قبل النشر وأنشئ رابطًا جديدًا. للحماية الأقوى لاحقًا استخدم Bot يولّد دعوة أحادية الاستخدام ويلغي وصول العضو عند انتهاء الاشتراك؛ القفل الحالي يمنع كشف الرابط من فوس لكنه لا يستطيع سحب نسخة سبق نسخها.

## 6. الصفحات المطلوبة لـ Tap

الصفحات العامة موجودة دون تسجيل دخول:

- `/pricing` الأسعار ووصف الباقات المتجددة.
- `/about` نبذة عن فوس والمالك.
- `/privacy` سياسة الخصوصية.
- `/terms` الشروط والأحكام وشروط التجديد والإلغاء.
- `/refund-policy` سياسة الاسترداد/التصحيح المالي.

وجود صفحة «سياسة الاسترداد» لا يعني منح استرجاع اختياري لكل استخدام. النص يفرّق بين:

- إيقاف التجديد: يمنع الخصم القادم مع استمرار الوصول حتى نهاية المدة.
- الاسترداد: لا يُمنح بعد بدء استخدام المحتوى الرقمي لمجرد تغيير الرأي، مع معالجة الخصم المكرر، وعدم التفعيل، وأي حق إلزامي نظامًا.

بريد خدمة العملاء مضبوط على `phoslearn@gmail.com`. بعد نشر هذه النسخة أرسل إلى Tap الرابط الجذري نفسه: `https://phoslearn.vercel.app/`، وليس رابطًا محليًا ولا رابط ملف ZIP.

## 7. اختبار Sandbox كامل

1. شغّل مخطط Supabase الجديد وأضف متغيرات الاختبار.
2. سجّل الدخول بحساب اختبار.
3. اختر باقة، واملأ الاسم والجوال، وتأكد أن مربع الموافقة على التجديد غير محدد افتراضيًا.
4. وافق صراحة، ثم أكمل الدفع ببطاقة Sandbox من Tap.
5. راجع سجل Charge وتأكد أن المبلغ والعملة والخطة صحيحة، وأن الرد يحتوي Customer/Card/Payment Agreement IDs.
6. تأكد أن حالة الطلب تصبح `paid` وأن الذكاء الاصطناعي والمجتمع يفتحان للحساب نفسه.
7. أعد إرسال webhook نفسه وتأكد أن المدة لا تتكرر.
8. اختبر بطاقة مرفوضة، إغلاق صفحة الدفع، تأخر webhook، وانقطاع الطلب؛ يجب ألا تتكوّن عمليتا دفع متداخلتان.
9. نفّذ Cron يدويًا مع `Authorization: Bearer <CRON_SECRET>` في بيئة اختبار، وتأكد أن التجديد يستخدم المبلغ نفسه ولا يعمل قبل الموعد.
10. ألغِ التجديد قبل نهاية المدة، وتأكد أن `auto_renew` يتوقف وأن الوصول يبقى حتى النهاية، وأن Cron لا ينشئ دفعة الدورة التالية.
11. في Sandbox فقط، اختبر الإلغاء بعد حلول موعد التجديد: يجب أن تُصالح الدورة المستحقة مرة واحدة إن كانت بدأت، ثم يتوقف كل ما بعدها، ولا يسمح النظام بفتح اشتراك أولي منافس أثناء ذلك.
12. اختبر تبديل الحساب وتسجيل الخروج؛ يجب ألا تبقى مزايا الحساب السابق مفتوحة.

لا تنتقل إلى Live ما لم تنجح هذه الدورة كاملة ويعتمد Tap إعداد حفظ البطاقة وMIT لحسابك.

## 8. الاسترداد والاعتراضات التشغيلية

لا توفر الواجهة زر استرداد تلقائي. إذا احتجت تصحيح خصم مكرر أو عدم تفعيل، نفّذ الاسترداد من لوحة Tap بعد التحقق. راجع فورًا سجل Tap وسجل `payment_orders` وأوقف التجديد للحساب المتأثر.

عند وصول webhook لاسترداد مؤكد، يجلب الخادم Refund وCharge من Tap ويجمع الاستردادات الجزئية المؤكدة للعملية نفسها. إذا بلغ مجموعها كامل قيمة العملية، يلغي الوصول الموافق لها آليًا؛ أما الاسترداد الجزئي فيبقى للمراجعة اليدوية لأن تحويله إلى مدة وصول ليس محددًا. اختبر هذا المسار في Sandbox، وتعامل مع اعتراضات الدفع يدويًا حتى تعتمد لها سياسة ومسارًا منفصلين.

## 9. معلومات الانضمام المقترحة لـ Tap

- **المالك:** احمد عبدالعزيز احمد الرفاعي — `Ahmed abdulaziz alrefaei`، مع الالتزام بالتهجئة الإنجليزية المطابقة لشهادة الآيبان.
- **النشاط:** منصة تعليمية رقمية تساعد الطلاب على المذاكرة، وتقدم مزايا مدفوعة تشمل الشرح الذكي والمجتمع الخاص.
- **الموقع بعد نشر النسخة:** `https://phoslearn.vercel.app/`
- **المبيعات المتوقعة أول شهر:** قرابة 50 اشتراكًا موزعة بين الباقتين، بإجمالي متوقع 1,000–2,000 ر.س شهريًا.
- **المرفقات المطلوبة:** السجل التجاري أو وثيقة العمل الحر المطابقة للنشاط، وشهادة آيبان مصدقة من البنك يظهر فيها اسم المستفيد بالإنجليزية.

## الملفات المهمة

- `api/checkout.js`: إنشاء أول Charge مستضاف بالسعر الخادمي والموافقة الصريحة.
- `api/tap-webhook.js`: تحقق توقيع Tap ثم المصالحة عبر Retrieve Charge.
- `api/renew-subscriptions.js`: التجديد المتكرر المحمي بـ Cron secret والإديمبوتنسي.
- `api/subscription-cancel.js`: إيقاف الخصم القادم مع إبقاء الوصول الحالي.
- `api/payment-status.js`: استعادة حالة الدفع بعد رجوع العميل.
- `api/ai.js` و`api/community.js`: حماية المزايا المدفوعة.
- `supabase/schema.sql`: الجداول وRLS والأقفال والدوال الخادمية.
